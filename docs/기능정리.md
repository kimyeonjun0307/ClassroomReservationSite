# 강의실 예약 시스템 - 역할별 기능 정리 (v2)

> 이 문서는 DB를 다시 짜기 전에 "무슨 기능이 필요한지"부터 확정하기 위한 정리본입니다.
> 지금 코드(index.html/manager.html/admin.html)에 실제로 구현된 것 + 교수님이 요청하신 건물 등록,
> 그리고 최종관리자가 전체 총괄이라는 정정된 역할 범위를 반영했습니다. 여기서 기능을 최종 확정한
> 다음에 그걸 기준으로 DB 테이블/컬럼/RLS를 다시 설계하는 순서로 가면 됩니다.
>
> **v1 → v2 변경점**: 최종관리자를 "건물 1개 담당"으로 잘못 정리했던 걸 "전체 건물/강의실 총괄"로 정정.

---

## 0. 역할 3단계

| 역할 | 코드상 이름 | 화면 | 관리 범위 |
|---|---|---|---|
| 예약자(조교) | `assistant` | index.html (메인) | 본인 예약만 |
| 중간관리자 | `mid_admin` | manager.html | 본인이 배정받은 강의실만 (건물 무관, 여러 건물 것이 섞여있어도 됨) |
| 최종관리자 | `final_admin` | admin.html | **전체 건물 / 전체 강의실 (총괄)** |

가입 직후엔 전부 `assistant`로 시작 → 최종관리자가 승격시켜줌.

> **[수정] 최종관리자는 건물에 종속되지 않습니다.** 특정 건물 하나를 담당하는 게 아니라
> 시스템 전체(모든 건물, 모든 강의실)를 관리하는 최상위 관리자입니다. 같은 건물이라도
> 여러 단과대가 나눠서 쓸 수 있기 때문에, 강의실을 중간관리자에게 배정하는 것도
> "건물 단위"가 아니라 최종관리자가 **강의실 하나하나를 직접 골라서** 배정하는 방식입니다.
> (이전 버전 문서에서 "최종관리자 1명 = 건물 1개"로 정리했던 건 잘못된 이해였습니다 — 정정합니다.)

---

## 1. 예약자 (메인 화면)

- 회원가입 / 로그인 / 로그아웃
- 조건 검색: 건물, 공간유형, 기자재, 최소 수용인원
- 검색 결과 목록 + 층별 필터
- 강의실별 예약 현황을 날짜 단위 타임라인으로 조회
  - 표시 구분: 정기수업(회색, 예약불가) / 다른 사람 예약(회색, 상세 비공개) / 내가 신청한 것(노란색)
- 강의실 상세정보 확인: 수용인원, 보유 기자재, 이용수칙, 문의처(담당부서/전화/이메일)
- 일일 대여 신청: 날짜+시간대 드래그 선택, 대여목적, 이용인원 입력 후 신청
- 즐겨찾기 등록/해제, "즐겨찾기만 보기" 필터
- 마이페이지: 내 예약 목록, 상태별(대기/승인/거절/취소/완료) 필터, 예약 취소

---

## 2. 중간관리자

- 로그인 (본인 담당 강의실만 보임)
- 담당 강의실 목록 + 층별 필터
- 담당 강의실 전체를 날짜 단위 타임라인으로 조회
- 예약 건 승인 / 거절 (+ 코멘트)
- 승인 대기 목록 한 번에 모아보기
- 담당 강의실 정보 수정: 강의실명, 수용인원, 이용수칙, 문의처(담당부서/전화/이메일)
- 정기수업(고정 시간표) 등록: 학기 선택, 강의실, 요일×시간(복수 가능), 과목명, 담당교수, 수강인원
- 로그아웃

---

## 3. 최종관리자 (전체 총괄)

- 로그인
- **건물 등록/관리 (신규)** — 건물명, 문의처(담당부서/전화/이메일), 기자재 사용 여부 등을 등록.
  건물 개수 제한 없이 계속 추가 가능. 총괄 관리자라 자기 소속 건물 같은 게 없어도 새 건물을 바로 만들 수 있음.
- 강의실 관리 (전체 건물 대상)
  - 추가 (건물 선택, 층, 호실번호, 강의실명, 공간유형, 수용인원)
  - 상태 변경: 사용가능 / 공사중 / 리모델링예정 / 사용중지 — **어느 건물의 강의실이든** 변경 가능
  - 숨기기(소프트 삭제 — 예약 기록 보존을 위해 완전삭제는 안 함)
  - 담당 중간관리자 배정 현황 확인
- 중간관리자 관리
  - 기존 assistant 계정을 mid_admin으로 승격
  - **담당 강의실 배정** — 건물 상관없이 전체 강의실 목록에서 체크박스로 골라서 이 중간관리자에게 부여
    (한 중간관리자가 A건물 3층 + B건물 1층처럼 건물을 넘나드는 강의실을 같이 담당할 수도 있음)
  - 담당 강의실 권한 수정(체크박스로 추가/해제)
  - 담당 해제(계정 삭제 아님 — role을 assistant로 되돌림)
- 학기 관리: 학기명/시작일/종료일 CRUD (모든 중간관리자에게 공통 노출)
- 로그아웃

## 4. 지금 코드엔 없지만 있으면 정상적인 기능 (검토 후보)

- 공간유형(room_types) 마스터 관리 화면 — 지금은 DB에 4종 고정, 관리자가 추가/수정하는 UI 없음
- 기자재(equipment) 마스터 관리 화면 — 위와 동일
- 예약 승인/거절 이력(감사로그) 조회 화면 — DB에 테이블(`booking_logs`)은 있는데 그걸 보여주는 화면이 없음
- 알림 기능 — 화면에 종 아이콘만 있고 실제 알림 로직 없음
- 통계/대시보드 (건물별/강의실별 이용률 등)

## 5. 역할 범위 확정 (수정됨) — DB에 미치는 영향

최종관리자가 전체 총괄이라는 게 확정됐으니, DB 쪽에서 바뀌어야 할 부분을 미리 정리해둡니다
(아직 코드는 안 고쳤습니다, 확인만 받고 진행하겠습니다).

- `assistants.building_id` 컬럼 자체가 필요 없어짐 → **삭제 대상**
  - 최종관리자: 애초에 특정 건물에 속하지 않으니 불필요
  - 중간관리자: 담당 강의실은 `rooms.manager_id`로 이미 직접 연결되니, 건물 소속을 따로 안 둬도 됨
- RLS 정책 재작성 필요: 지금 `rooms_manage_by_final_admin` 등이 "같은 건물일 때만" 허용하게
  되어 있는데, 이 조건을 없애고 **role이 final_admin이면 전체 강의실 대상으로 허용**하게 바꿔야 함
- `buildings` 테이블 자체는 그대로 두되, 최종관리자면 누구나 새 행을 추가할 수 있게 INSERT 권한 부여
- 이번에 겪었던 "새 건물을 최초로 누가 만드냐"는 문제(이전 문서 5번 항목)가 자연스럽게 해결됨
  — 최종관리자가 아무 때나 새 건물을 등록하면 되니까 별도 부트스트랩 단계가 필요 없어짐

## 6. 지금까지 실무에서 걸렸던 문제들 (DB 재설계 시 반영할 것)

- 프론트에서 새 로그인 계정을 직접 만들 수 없음 (서비스 키를 브라우저에 둘 수 없어서) →
  "계정 생성"과 "권한 부여"는 항상 분리된 단계여야 함
- `rooms`/`assistants` 등에 RLS가 걸려있어서, 관리 화면에서 UPDATE가 조용히 0건 처리되는 경우가
  있었음 → 이번에 `.select()`로 반영 건수를 확인하고 실패 시 알림 띄우도록 고쳤지만, 애초에
  권한 설계를 더 명확히 하면 이런 문제가 줄어듦
- PostgREST 스키마 캐시가 최신 상태로 안 맞을 때가 있었음 (SQL Editor로 직접 스키마를 바꿔서 생긴
  문제로 추정) → 마이그레이션을 통해서만 스키마를 바꾸는 흐름을 지키는 게 안전
