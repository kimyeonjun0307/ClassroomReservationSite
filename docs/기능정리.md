# 강의실 예약 시스템 - 역할별 기능 정리 (v4)

> 이 문서는 지금 실제로 동작하는 기능을 역할별로 정리한 것입니다.
>
> **v3 → v4 변경점 (2026-09-08)**: 계정을 새 Supabase 프로젝트(`yclrlgcixldovbhygjrc`)로
> 갈아탄 뒤 실제 코드/DB를 다시 확인해보니 v3가 설명하던 "가입 신청 → 최종관리자 승인" 흐름,
> "건물 등록" UI가 실제 코드엔 없는 걸 확인해서 걷어냈습니다 (아래 1번, 4번 참고). DB 쪽 상세
> 차이는 `db/schema.sql` 상단 주석 및 이 문서 6번 항목 참고.

---

## 0. 역할 3단계

| 역할 | 코드상 이름 | 화면 | 관리 범위 |
|---|---|---|---|
| 예약자(조교) | `assistant` | index.html (메인) | 본인 예약만 |
| 중간관리자 | `mid_admin` | manager.html | 본인이 배정받은 강의실만 (건물 무관) |
| 최종관리자 | `final_admin` | admin.html | 전체 건물 / 전체 강의실 (총괄) |

가입 직후엔 전부 `assistant`로 시작. 다른 역할이 필요하면 **최종관리자가 admin.html에서 직접
승격**시켜야 함 (아래 4번 "중간관리자 관리" 참고 — 본인이 신청하는 절차는 없음). 최종관리자는
건물에 종속되지 않고 시스템 전체를 관리합니다.

---

## 1. 회원가입 / 로그인 (공통, login.html)

- 회원가입: 이름(선택) / 이메일·비밀번호(필수) 입력. **역할 선택 UI 없음** — 가입하면 무조건
  `assistant`로 생성됨 (코드 주석: "가입 시 role은 항상 'assistant'로 고정되므로 건물 선택 UI는
  제거됨"). mid_admin/final_admin이 되려면 이미 가입된 계정을 최종관리자가 승격시켜야 함
- 로그인: 이메일/비밀번호만 입력. 역할을 따로 고르지 않고, 로그인 성공 시 DB에 저장된 실제 role
  기준으로 index.html / manager.html / admin.html 중 하나로 자동 이동
- 아이디 저장(로컬 기억), 로그아웃

> v3까지 있던 "중간관리자·최종관리자로 가입 신청 → `role_requests`에 승인 대기 → 최종관리자 승인"
> 흐름은 실제 코드/DB엔 없습니다 (`role_requests` 테이블 자체가 없고, admin.html에도 승인 탭이
> 없음). 문서만 앞서 나가 있던 부분이라 이번에 정정.

---

## 2. 예약자 (메인 화면, index.html / mypage.html)

- 조건 검색: 건물, 공간유형, 기자재, 최소 수용인원
- 검색 결과 목록 + 층별 필터. **담당 중간관리자 배정 여부와 무관하게 해당 건물의 강의실 전부 노출**
- 강의실별 예약 현황을 날짜 단위 타임라인으로 조회
  - 표시 구분: 정기수업(회색, 예약불가) / 다른 사람 예약(회색, 상세 비공개) / 내가 신청한 것(노란색)
- 강의실 상세정보 확인: 수용인원, 보유 기자재, 이용수칙 (문의처 박스는 UI에 남아있지만 `buildings`에
  문의처 컬럼이 없어져서 코드상 항상 숨김 처리됨 — index.html 해당 부분 주석 참고)
- 일일 대여 신청: 날짜+시간대 드래그 선택, 대여목적, 이용인원 입력 후 신청
- 즐겨찾기 등록/해제, "즐겨찾기만 보기" 필터
- 마이페이지
  - 내 예약 목록, 상태별(대기/승인/거절/취소/완료) 필터, 예약 취소
  - **회원정보 수정**: 이름 변경, 비밀번호 변경

---

## 3. 중간관리자 (manager.html)

- 담당 강의실 목록 + 층별 필터 (본인에게 배정된 강의실만, 건물 무관)
- 담당 강의실 전체를 날짜 단위 타임라인으로 조회
- 예약 건 승인 / 거절 (+ 코멘트)
- 승인 대기 목록 한 번에 모아보기
- 담당 강의실 정보 수정: 수용인원, 이용수칙, 썸네일 (강의실명·문의처 컬럼이 DB에 없어서 수정 대상 아님)
- 정기수업(고정 시간표) 등록: 학기 선택, 강의실, 요일×시간(복수 가능), 과목명, 담당교수

---

## 4. 최종관리자 (admin.html, 전체 총괄)

실제 탭은 3개뿐입니다: **강의실 관리 / 중간관리자 관리 / 학기 관리**.

- **건물 관리 UI 없음**: 건물 추가/수정 화면이 코드에 없습니다. 강의실 등록 시 기존 건물 중
  골라서 연결만 가능. 새 건물이 필요하면 지금은 Supabase 대시보드(Table Editor/SQL Editor)에서
  `buildings` 테이블에 직접 INSERT해야 합니다
- **강의실 관리** (전체 건물 대상)
  - 추가 (건물 선택, 층, 호실번호, 강의실명, 공간유형, 수용인원)
  - 상태 변경: 사용가능 / 사용중지 (2단계뿐 — `rooms.is_active` boolean. 공사중/리모델링예정 같은
    세부 상태는 UI에 남은 죽은 CSS 클래스만 있고 실제 선택지는 없음)
  - 숨기기 (소프트 삭제 — 예약 기록 보존을 위해 완전삭제는 안 함)
  - 담당 중간관리자 배정 현황 확인 (건물별로 그룹핑되어 표시)
- **중간관리자 관리**
  - 기존 assistant 계정을 mid_admin으로 승격 + 담당 강의실 배정 (건물 무관, 체크박스로 다건 선택)
  - 담당 강의실 권한 수정, 담당 해제(계정 삭제 아님 — role을 assistant로 되돌림)
- **학기 관리**: 학기명/시작일/종료일 CRUD (모든 중간관리자에게 공통 노출)

## 5. 아직 없는 기능 (후보)

- 공간유형(room_types)/기자재(equipment) 마스터 관리 화면 — DB엔 있는데 추가/수정 UI 없음 (지금은 고정 4종/4종)
- 건물 추가/수정 화면 — `buildings` 테이블은 있는데 admin.html에 건물을 등록하는 UI가 없음
- 문의하기(index.html "📩 문의하기") — 코드는 있는데 `inquiries` 테이블이 DB에 없어서 등록 시
  에러남 (팀원이 별도로 처리하기로 함)
- 예약 승인/거절 이력 화면 — `booking_logs` 같은 감사로그 테이블 자체가 DB에 없음 (v3 설계안에만
  있었음). 지금은 `bookings.reviewed_by`/`reviewed_at`으로 "최근 처리 1건"만 남음
- 이메일 변경 — 지금은 Dashboard(Authentication → Users)에서만 가능, 앱 내 자기 이메일 변경 기능 없음
- 알림 기능 — 종 아이콘만 있고 실제 알림 로직 없음
- 통계/대시보드 (건물별/강의실별 이용률 등)
- `bookings.status = 'done'` 자동 전환 — DB에 이 상태로 넘겨주는 함수/pg_cron이 없음. 지금은
  예약 날짜가 지나도 `approved` 상태로 남아있을 것으로 보임 (직접 확인 필요)

## 6. 새 Supabase 계정(`yclrlgcixldovbhygjrc`)으로 전환하며 확인된 것 (2026-09-08)

- 이전 계정 대비 스키마가 많이 단순해짐: `assistants`→`users` 개명, `room_status`/`booking_action`
  enum 없음, `role_requests`/`booking_logs`/`inquiries` 테이블 없음, `rooms`에서
  `room_name`/`area`/`pc_count`/`managing_dept`/`manager_name`/연락처 컬럼 삭제. 정확한 컬럼
  목록은 `db/schema.sql` 참고 (2026-09-08 실제 DB 조회 결과 기준으로 재작성함)
- **정규강의 스케줄이 안 보이던 원인**: `semesters` 테이블이 완전히 비어있었음(0행) → "현재 학기"가
  없어서 index.html/manager.html이 정기수업을 아예 안 그림. admin.html "학기 관리" 탭에서 학기
  추가 + "현재 학기로 설정"을 해야 그 다음부터 정규강의 등록/표시가 됨 (코드 버그 아님, 데이터 설정 누락)
- `users` 테이블 RLS: "본인 또는 final_admin 조회" 정책 말고 "로그인한 사용자는 서로 이름 조회
  가능"(조건 없이 true)이 같이 걸려있어서, 실질적으론 로그인한 사람이면 누구나 다른 사용자 행을
  전부 조회 가능한 상태 (좁은 정책이 사실상 죽어있음)
- `bookings` INSERT 정책이 `requester_id = auth.uid()`만 확인하고 role은 안 봐서, mid_admin/
  final_admin 계정으로도 예약 신청 자체는 가능함

## 7. 실무에서 겪은 문제들 (참고용 - 계속 누적 중)

- 프론트에서 새 로그인 계정을 직접 만들 수 없음 (서비스 키를 브라우저에 둘 수 없어서) →
  "계정 생성"과 "권한 부여"는 항상 분리된 단계 (지금은 가입=assistant 고정, 승격은 최종관리자가 UI에서)
- RLS로 막힌 UPDATE는 에러 없이 0건 처리됨 → `.select()`로 반영 건수 확인하고 실패 시 알림 띄우는
  패턴을 전 화면에 적용함
- PostgREST는 두 테이블 사이에 FK가 2개 이상이면(예: `rooms.manager_id`+`favorites` 경유,
  `bookings.requester_id`+`bookings.reviewed_by`) `테이블명(컬럼)` 형태로 embed 시 "관계가
  여러 개라 모호하다"는 에러를 냄 → `테이블명!fk컬럼명(컬럼)`으로 명시해야 함
- `auth.users.email`을 Table Editor로 직접 고치면 `auth.identities`가 안 맞아서 로그인이 옛날
  이메일 기준으로 계속 동작함 → 이메일 변경은 반드시 Authentication 패널이나 `auth.updateUser()`로
- 계정 삭제는 예약/학기/정기수업 등이 그 계정을 참조하고 있으면 FK 때문에 막힘 → `is_active=false`로
  비활성화하는 게 정석 (로그인 시 앱에서 바로 튕겨내도록 이미 구현됨)
